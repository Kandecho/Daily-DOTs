# 工作流程（给维护 agent）

你可能是 ChatGPT 的 Dot、Codex、Claude 或别的 agent。下面的规则对谁都一样；遇到与你所在平台默认习惯冲突的地方，以本文件为准。

## 先弄清楚

- 这是仓库所有者自己读的日报。目标是每天能顺利读到一期，不是做成产品。
- 原稿在进仓库之前已经完成写作和核实。你的工作是排版、发布和维护程序，不是重写新闻。
- 任务没有说清楚的编辑决定（删一条、改标题、换来源、改版式）先问所有者。
- 日常发期由一个主代理负责，直接提交到 `main`。改排版、程序或文档时常有多个 agent 参与，这类改动走分支和 PR。

## 能改什么

| 内容 | 规则 |
| --- | --- |
| 原稿正文、标题、来源 | 只按所有者的明确要求改。发现事实或文字问题时报告，不顺手改 |
| 原稿元数据（`layout`、地图组件等） | 可以按 [排版约定](排版约定.md) 补全或修正，改完重新生成 |
| 本地 HTML、`_site/` | 只能由程序生成，不手改、不提交；云端本地原稿与 HTML 留档保留 |
| `tools/`、`tests/`、`docs/`、README | 工程改动，走分支和 PR（见下文） |
| 字体文件、`_build/`、`_site/`、虚拟环境、本机路径、账号、令牌 | 不进 Git，也不要用 `git add -f` 绕过 `.gitignore` |

刊名只在 `tools/core.py` 定义：报头 `NAME`，副题 `SUBTITLE`。原稿 `title` 必须等于 `SUBTITLE`。

## 发布一期

1. 把原稿放到 `editions/YYYY-MM-DD/原稿_YYYY-MM-DD.md`，目录日期、文件名日期和 `issue_date` 必须一致。没写完的稿子不要放进 `editions/`。
2. 用 `python tools/daily.py editions/YYYY-MM-DD/原稿_YYYY-MM-DD.md` 生成本期本地留档，再用 `python tools/site.py --build` 统一构建检查 `_site/`。缺字体先跑 `python tools/fetch_fonts.py`；失败就修原稿或环境，不绕过检查、不发布中间文件。
3. 打开 `_site/index.html` 和本期 HTML 看一遍（手机宽度，约 390px）：
   - 目录页的日期、条数、标题对；点进去是对应的那条；
   - 没有缺字、截断、横向溢出；地图标签不重叠，和图注对得上；
   - 左右翻页、页内上下滚动、「回到目录」「首页」都能用；
   - 明暗两种主题都看得清。
   程序检查不等于真机检查；没看成就如实说没看。
4. 只提交本期原稿，直接推送到 `main`，不开 PR。Actions 会重建全部期次和首页并发布 Pages；本地 HTML 留着，不入 Git。

修订已经发布的一期：先改原稿，再加 `--overwrite` 重新生成。修订说明写在提交信息里，不写进页面。`--overwrite` 不能覆盖另一个日期的成品。

## 改程序、模板或文档

- 从 `main` 开分支，提交后开 PR，不直接推 `main`。PR 里说明改了什么、为什么、怎么验证的，方便其他 agent 审查或接手。
- 改了版式或交互：更新测试，跑 `python -m unittest discover -s tests`，再用浏览器看一期真实日报。
- 改了生成结果：用 Python 3.12 跑 `python tools/site.py --build` 重建全部期次检查；PR 只含源码、测试和必要文档，不含生成的 HTML。合并后由 Actions 构建发布。
- 测试用的虚构数据要标 `TEST`，不能当新闻发布。

## 提交前检查

```sh
git status --short
git diff --check
git diff --cached --stat
```

- 只包含这次需要的原稿或工程文件；本地 HTML 已按当前原稿生成。
- 没有账号、令牌、私人对话、本机路径、字体文件或生成输出。
- 提交作者用仓库已经配置好的身份，不要冒用别人的名字和邮箱。

## 推送之后

推送成功不等于网站已经更新。确认 Actions 的构建和 Pages 部署都成功，再打开 <https://kandecho.github.io/Daily-DOTs/> 看最新一期。构建或检查失败时不发布，线上保留上一版；不能只凭推送成功就说「已发布」。
