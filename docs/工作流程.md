# 工作流程

贡献范围、分支与提交说明见 [贡献指南](../CONTRIBUTING.md)；原稿格式和版式见 [排版约定](排版约定.md)。

刊名只在 `tools/core.py` 定义：报头 `NAME`，副题 `SUBTITLE`。原稿 `title` 必须等于 `SUBTITLE`。

## 采编至定稿

本节适用于已授权的上游搜索、选题和写稿，不扩大下游维护者改写已定稿新闻的权限。[新闻采编原则](采编原则.md)统一维护报道目标、必要性与充分性、事实核验和栏目标准；本节只规定执行顺序，原有选题范围与截点要求继续适用。

### 新闻候选准备（主新闻与探索）

以下准备要求适用于主新闻与探索项。趣闻按自身内容形式准备材料，并依[共同事实核验与时间边界](采编原则.md#共同事实核验与时间边界)中的趣闻要求核实事实，不以当日新增或事件经过为前提；随后走末页路线。

1. 确定这条报道需要向读者讲清什么，形成可修正的着眼点：它显出了什么变化，或带来了什么新的认识。着眼点用于发现材料缺口，不是预设结论后寻找佐证。
2. 按[共同事实核验与时间边界](采编原则.md#共同事实核验与时间边界)核实候选，并搜集事件经过及理解它所需的背景、比较基准、联系和具体后果。缺什么定向补查，再按[栏目任务](采编原则.md#栏目任务)选择下列路线。

### 主新闻：先第一格，再第二格

1. 先写“今天发生了什么”，随后检查并修改：本次新增、经过、结果是否讲清，时间与事实边界是否准确，属于同一事实链的信息是否放在一起。材料不足先补查，不为给第二格留内容而拆开事件。
2. 基于检查后的第一格，再写“为什么值得今天留下”。确认读者还需要什么背景、比较、联系或后果才能理解变化，再组织对应材料；具体分工见[信息分配与口吻](采编原则.md#信息分配与口吻)。不能把第一格的剩余材料直接填进来。
3. 两格连起来读，按共同原则检查整条报道是否必要、充分、连贯。第二格暴露的缺口可以促使回改第一格、补查或重新考虑选题，不把先后顺序当作不可回改的流水线。

这是起草与检查的顺序，不要求先写一篇不分格的全文，也不要求另存中间稿。篇幅随理解需要，不以段落数或字数判定完成。

### 末页：探索或趣闻

有合适的当日探索项时，围绕新增发现组织事件、认识支点与重要不确定性；必要限定依其解释作用安排，不机械套用主新闻两格起草顺序，也不把核验记录作为固定正文。没有合适探索项，转用[趣闻备用页](趣闻页.md)，按其内容形式写作，不强加新闻式两格。两者共用末页，尽量每天保留这一页，定稿只留一种。

### 定稿交接

各路线都在采编阶段按共同原则补足材料、组织并检查全文。完成后才进入排版发布；定稿后不追加全面事实复审或模型审稿，保留下述轻量正文、资源和导航检查。

## 发布一期

1. 把原稿放到 `editions/YYYY-MM-DD/原稿_YYYY-MM-DD.md`，目录日期、文件名日期和 `issue_date` 必须一致。没写完的稿子不要放进 `editions/`。
2. 用 `python tools/daily.py editions/YYYY-MM-DD/原稿_YYYY-MM-DD.md` 生成本期本地留档，再用 `python tools/site.py --build` 统一构建检查 `_site/`。缺字体先跑 `python tools/fetch_fonts.py`；失败就修原稿或环境，不绕过检查、不发布中间文件。
3. 打开 `_site/index.html` 和本期 HTML 看一遍（手机宽度，约 390px）：
   - 目录页的日期、条数、标题对；点进去是对应的那条；
   - 没有缺字、截断、横向溢出；地图标签不重叠，和图注对得上；
   - 左右翻页、页内上下滚动、「回到目录」「首页」都能用；
   - 明暗两种主题都看得清。
   程序检查不等于真机检查；没看成就如实说没看。
4. 提交并推送本期原稿。Actions 会重建全部期次和首页并发布 Pages；本地 HTML 留着，不入 Git。

修订已经发布的一期：先改原稿，再加 `--overwrite` 重新生成。修订说明写在提交信息里，不写进页面。`--overwrite` 不能覆盖另一个日期的成品。

## 改程序、模板或文档

- 改了版式或交互：更新测试，跑 `python -m unittest discover -s tests`，再用浏览器看一期真实日报。
- 改了生成结果：用 Python 3.12 跑 `python tools/site.py --build` 重建全部期次检查。合并后由 Actions 构建发布。
- 测试用的虚构数据要标 `TEST`，不能当新闻发布。

## 提交前检查

```sh
git status --short
git diff --check
git diff --cached --stat
```

对照 [贡献范围](../CONTRIBUTING.md#贡献范围) 确认暂存区只含这次需要的文件；涉及原稿改动时，本地 HTML 已按当前原稿生成。

## 推送之后

推送成功不等于网站已经更新。确认 Actions 的构建和 Pages 部署都成功，再打开 <https://kandecho.github.io/Daily-DOTs/> 看最新一期。构建或检查失败时不发布，线上保留上一版；不能只凭推送成功就说「已发布」。
